Scope version: **2026-09-19.2**.

**For full audit applicability, use the [program-wide control/evidence catalog](audit/README.md) and [per-service matrix](audit/SERVICE_MATRIX.md).** They cover all 23 services across identity, exposure, at-rest and transit protection, credential lifecycle, audit, configuration, vulnerabilities, recovery, inventory, incident response and governance, with a review of all 20 NIST families. The matrix below describes current encryption implementation maturity only. It does not limit program applicability.

The program is intended to collect fresh, deterministic evidence frequently and retain history ready for audit or other authorized use. These services are in scope across applicable NIST controls, with candidate mappings now documented in the program-wide catalog; final selection remains subject to RCSA/control-owner/auditor agreement. The matrix below records encryption coverage, provisionally mapped to **SC-28 / SC-28(1)**. Applicability must be selected per service and control. A service without its own encryption switch can still have other applicable controls.

## How to read the matrix

These are implementation coverage categories, not findings from a tenant:

- **Supported, scoped:** a reviewed encryption rule exists for the stated storage boundary; reads, service/tier validation and dependencies must still succeed. This is not whole-service or whole-workload coverage.
- **Partial:** some metadata, component guarantee or dependency checks exist; material service/workload evidence remains unverified. A narrower component may report PASS without closing the gaps.
- **Unsupported:** no reviewed handler for the exact ARM type. The current collector records UNSUPPORTED if ARM inventory returns it; it does not promise discovery of every child resource.
- **Not collected (Graph):** outside the ARM inventory plane entirely. The current report cannot even emit an UNSUPPORTED row for an undiscovered application object.
- **Justified encryption N/A:** the current encryption rule treats the resource as an identity/network construct, with inventory identity only. The resource remains in program scope for other selected controls.

Rollup of the **23 service entries below**: 8 supported within stated scope, 8 partial, 4 unsupported, 1 not collected through Graph, and 2 justified encryption N/A. This is not a pass rate. Exact current handlers, API versions and guarantee sources remain in [COVERAGE.md](COVERAGE.md).

## Identity and permission boundary

An app registration is an Entra application object, not a subscription resource or the same object as its enterprise application/service principal. The Graph collector scopes the explicit tenant and retains distinct object and client/app IDs, and treats service principals separately. Selected-application filtering is not implemented; enabled Graph collection covers the configured tenant. ARM subscription enumeration neither discovers these objects nor demonstrates their absence. [Microsoft application/service-principal model](https://learn.microsoft.com/en-us/entra/identity-platform/app-objects-and-service-principals).

For organization application listing, Microsoft documents `Application.Read.All` as the least-privileged delegated or application permission for the list API. Any future use needs separately authorized Graph permissions/consent and the correct tenant; existing subscription Reader grants do not supply them. The opt-in Graph adapter requests a separate Graph token and verifies tenant identity; see [its exact scope and permissions](CONFIGURATION_ASSESSMENTS.md). No consent change, Graph request or personal-tenant access is authorized or performed by this scope document. Metadata selection must avoid secret/private-key values. [Microsoft Graph permissions for listing applications](https://learn.microsoft.com/en-us/graph/api/application-list?view=graph-rest-1.0).

## Private endpoint ownership boundary

Private endpoints are explicitly in program scope despite the earlier broad networking exclusion. Their current encryption N/A result is narrow: it says no customer at-rest data-store mechanism is assessed on that construct. It does **not** remove private endpoints from other selected controls or verify their configuration.

Future resource-local, read-only evidence may cover the endpoint's target service/subresource, connection/approval state and declared network/DNS relationships, with ownership recorded and the network team supplying evidence where needed. No VNet, subnet, route-table, NSG, DNS or shared network administration is added to the platform team's scope by this document. All network changes remain unauthorized here.

## Backing dependencies and retained handlers

The 23 entries describe program services, not an exhaustive list of storage types or a deletion/filtering instruction. Preserve discovered backing dependencies even when they are not standalone entries:

- Managed disks, snapshots and managed images keep their existing scoped handlers. VM/VMSS/AKS conclusions still require appropriate node/instance/volume and temporary-storage evidence.
- Kubernetes volumes, CSI stores, Azure Files/blob mounts, Function host/content/deployment storage, Container Apps revisions/storage, Event Hubs Capture, Event Grid dead-letter/delivery stores and telemetry destinations must be resolved or explicitly left unverified.
- Backup source workloads, operational snapshots and restored/exported copies do not inherit a vault conclusion. Grafana, Prometheus, Application Insights and Log Analytics each retain their own storage/identity boundaries.
- Existing SQL/MI/Synapse TDE, MySQL, Kusto, AI Search, Service Bus, Mongo-cluster and legacy Redis handlers remain useful for discovered resources/dependencies. Their existence does not add them as new authoritative program service entries or implement additional NIST controls.

ARM traversal and unsupported-type reporting continue as implemented. The list does not authorize hidden omissions, deleting handlers or declaring every undiscovered child covered. A lack of tenant access here means neither deployment presence nor deployment absence is known.

## Deterministic core and future consumers

Collection, evaluation, local evidence archiving and PDF generation use deterministic Python/APIs with **no runtime AI/model dependency or model-call costs**. Preserve versioned machine-readable evidence, stable resource/rule identity, run/observation timestamps, inventory/coverage/errors and replayable snapshots for later historical retention and retrieval.

The current implementation preserves a configurable local filesystem archive and a self-contained PDF generated from one exact saved run; see [Local archive and PDF workflow](LOCAL_ARCHIVE_PDF.md). Optional later MCP consumers, knowledge bases, APIs and posture dashboards may read that evidence. The Blob adapter and Azure Functions collection/report entry points have offline tests and bounded personal-lab live validation. The temporary personal app is stopped with operations disabled and no timer. Workplace control selection, retention, scope and costs remain separate decisions; “no AI” does not mean zero hosting/storage cost. See [current status](STATUS.md). No MCP/AI/dashboard is implemented.

## Modular onboarding requirement and current extension points

The user requires new resource types to integrate with the common evidence path so they can participate in reports, local evidence storage and future queries without separate service-specific output stacks. Service-specific collection and control logic should produce stable, versioned common evidence records; reports, storage and future API/query consumers should consume those records generically. This is a design requirement, not a claim that a full plugin system or database exists today.

Current extension points are concrete Python modules:

- [catalog.py](../azure_at_rest/catalog.py) registers exact ARM types, rule ID/mode, API version, scope, source, safe property paths and known child collections in `RULES`.
- [collector.py](../azure_at_rest/collector.py) supplies live/fixture transports and normalized snapshots; [safety.py](../azure_at_rest/safety.py) projects safe fields. Custom collection, nested projections and dependency semantics still require code changes.
- [assessment.py](../azure_at_rest/assessment.py) dispatches rule modes and produces common result records; [verification.py](../azure_at_rest/verification.py) builds auditor commands from those records and the catalog, with some service-specific branches.
- [snapshot.py](../azure_at_rest/snapshot.py) validates replay inputs. [report.py](../azure_at_rest/report.py) and [cli.py](../azure_at_rest/cli.py) consume shared report/result structures to emit JSON and Markdown. There is no dynamic plugin discovery.
- [storage.py](../azure_at_rest/storage.py) defines the three-method object-store contract and local POSIX adapter. [archive.py](../azure_at_rest/archive.py) archives separate facts, saved conclusions and frozen context, then selects an exact historical run without recollection or reassessment. [pdf_report.py](../azure_at_rest/pdf_report.py) renders that saved run into one self-contained PDF with a distinct archived report identity.
- [Workplace Azure handoff](WORKPLACE_AZURE_HANDOFF.md) and its portable prompts describe the implemented Blob adapter, Functions host and remaining workplace configuration/live-validation gates. API/query consumers beyond the exact-run report operation remain unimplemented.

An onboarding change must preserve resource/rule identity, observation/assessment timestamps, evidence/source basis, result/reason, dependencies, gaps/errors and inventory completeness, and cover the normal, missing, denied and incomplete paths in offline fixtures. Additions to the record contract must be versioned and replay-compatible. A new service should reuse the common report path, with new safe projections and command semantics where necessary. Storage, future API/query and optional AI-read consumers should depend on this contract rather than import individual service handlers. Tenant/Graph objects require an explicit identity/collection-plane extension: the current ARM identity validator cannot simply accept a Graph object as another ARM resource.

The authorized [local Wiz integration](WIZ_INTEGRATION.md) now imports a project-defined normalized export, archives its exact bytes, compares inventory and findings with one exact Azure run, and verifies historical comparison reads. It preserves source observation time, identity, completeness and evidence meaning without modifying saved Azure assessments. Native Wiz authentication/API/export mapping remains unimplemented and unvalidated pending the actual workplace contract and access.

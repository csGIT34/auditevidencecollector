# Copyable workplace configuration and implementation prompt

Work in this cloud-governance repository. Inspect its actual current code and preserve unrelated changes. It implements version 0.3.2: deterministic Python evidence collection/assessment, local archival/PDF use, and a thin Azure Functions v2 hosting layer with managed identity and a create-only Azure Blob ObjectStore. Do not rebuild those parts from scratch or assume they are deployed. Read docs/AZURE_FUNCTIONS.md, docs/MACOS_DEVELOPMENT.md, docs/WORKPLACE_AZURE_HANDOFF.md, docs/LOCAL_ARCHIVE_PDF.md and the module contracts below. These instructions are self-contained and do not require earlier conversation context.

The intended product is macOS development/testing and production execution entirely inside Azure Functions, independent of a person's machine. Source transfers through an approved GitHub repository. Azure Automation is not the selected target. Two separate operations exist: scheduled collection -> deterministic assessment -> unique archived run; an explicitly requested saved-run PDF -> unique archived report. No automatic report after collection, latest-run substitution, recollection/reassessment for a historical PDF, public anonymous endpoint, database, dashboard, runtime AI, remediation or additional service collectors.

Program scope covers Event Hubs, AKS, App registrations, Event Grid, Storage Accounts, Cosmos DB, Managed Redis, Function Apps, Key Vaults, PostgreSQL Flexible Servers, Azure Container Apps, user-assigned managed identities, private endpoints, Azure Container Registries, backup vaults, App Configuration, Application Insights, Managed Grafana, Managed Prometheus, Log Analytics Workspaces, Virtual Machines, Virtual Machine Scale Sets and Automation accounts. docs/audit contains 215 proposed checks across all 20 NIST families. Executable assessment is still scoped encryption at rest, accepting provider-managed keys; do not represent the research as implemented or live-validated coverage.

Actual interfaces:
- function_app.py defines CollectEvidence (optional configured timer, no run-on-startup) and GenerateReport (FUNCTION-key-authorized POST /api/reports, exact run_id JSON only). Both remain disabled until enabled independently.
- azure_at_rest/hosting.py constructs strict Settings and execute(operation, run_id=...). It requires explicit subscriptions, selected identity and separate runtime/evidence accounts. It returns safe structured outcomes and logs stages. FAIL/INCOMPLETE audit findings do not fail a completed archive operation.
- azure_adapters.py defines token_credential, ArmCredential, verify_tenant and BlobStore. Production explicitly selects an attached user-assigned managed identity client ID. Its SDK credentials own refresh; no CLI session, automatic credential chain or unverified JWT parsing. Authenticated ARM subscription metadata verifies tenant/scope before collection. The report operation uses Blob authorization and deployment identity configuration, not new ARM evidence.
- BlobStore implements storage.ObjectStore.put_new(key, bytes), read(key), keys(prefix). Atomic conditional create-only block writes, exact bytes, complete pagination, portable key validation, bounded retries and sanitized errors are mandatory. Lost acknowledgements can reconcile only a matching per-attempt metadata marker plus exact bytes. Never adopt unrelated existing data, overwrite, provision accounts/containers, grant roles or change retention.
- workflow.py exposes reusable collect_run and assess_snapshot. archive.py saves/loads facts, conclusions and frozen context and publishes PDFs with completion manifests last. Old archive/snapshot/assessment schema-1.0 data stays readable; optional execution_provenance has its own schema. Retain every prior run/report and original binary PDF.
- pdf_report.py renders in memory and serializes shared ReportLab font state. Fonts come from ReportLab's package; program_scope.json is application package data. The auditor receives one self-contained PDF containing facts, criteria, results, methods, scope/times, limitations, dependency/error details, missing/manual/shared evidence and provenance. Internal JSON is not a human evidence dependency.
